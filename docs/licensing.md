# 라이선스 안내

이 문서는 Just Workspace 의 **운영자**, **수정본으로 서비스를 제공하는 자**, **이미지를 빌드해 재배포하는 자**가 준수해야 할 사항을 기술한다.
패키지·버전 단위 목록은 [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md) 에 있다.

사실(각 구성 요소의 포함 위치와 라이선스)과 해석이 필요한 사항을 구분해 기술한다. **해석 부분은 법률 자문이 아니다.** 이미지를 공개 배포하기 전에 [6. 배포 전 확인 필요](#6-배포-전-확인-필요)의 항목을 처리해야 한다.

## 1. 본 프로젝트 코드 — AGPL-3.0-or-later

이 리포의 소스는 **GNU Affero General Public License, 버전 3 또는 (선택에 따라) 그 이후 버전**으로 배포한다(SPDX: `AGPL-3.0-or-later`).

- 라이선스 전문: 리포 루트의 [`LICENSE`](../LICENSE) — 자유 소프트웨어 재단의 공식 문안과 동일하다.
- 저작권 고지와 적용 고지: 리포 루트의 [`NOTICE`](../NOTICE).
- 패키지 메타데이터(`package.json` 의 `license`)도 동일하게 표기한다.
- 플러그인에 대한 예외 조항은 **없다**(4절).
- 리포에 포함된 제3자 코드(`apps/desktop/native/vendor/` 등)에는 해당 폴더의 라이선스 파일이 적용된다.

AGPL 의 요구 사항을 사실 위주로 요약하면 다음과 같다. 정확한 조건은 전문을 참조한다.

| 이용 형태 | 적용 조건 |
|---|---|
| **수정 없이** 자체 서버에서 운영 | 추가 의무가 없다는 해석이 일반적이다. 제품에 표시되는 "소스 코드" 링크는 이 리포를 가리킨다 |
| **수정본**을 타인에게 네트워크 서비스로 제공 | 해당 서비스의 이용자에게 **수정본의 소스 코드**를 받을 기회를 제공해야 한다(13조). 2절 |
| 프로그램(소스·이미지)을 타인에게 **배포**(양도) | 동일 라이선스로, 라이선스 전문·저작권 고지와 함께, 해당 소스를 받을 수 있도록 제공해야 한다(4~6조) |
| 내부 사용에 한정(배포·서비스 제공 없음) | 배포·서비스 제공에 따른 조건은 적용되지 않는다 |

### 기여물의 조건

기여는 동일 라이선스(AGPL-3.0-or-later)로 접수한다. 기여자는 저작권을 보유하되, 프로젝트 저작권자에게 해당 기여물을 다른 라이선스 조건으로도 배포·재허가할 수 있는 권한을 부여한다 — 프로젝트가 향후 라이선스 조건을 변경하거나 별도 조건으로 제공할 수 있도록 하기 위함이다. 동의는 PR 템플릿의 확인란 표시로 갈음한다. 문안은 [CONTRIBUTING.md 의 "기여 조건"](../CONTRIBUTING.md#기여-조건).

## 2. 네트워크 서비스 제공자의 의무 (13조)

AGPL 과 GPL 의 차이점이다. 프로그램을 **수정**한 자는 그 수정본과 네트워크로 상호작용하는 모든 이용자에게 **해당 수정본의 소스 코드를 받을 기회**를 명확히 인지할 수 있는 방식으로 제공해야 한다.

제품은 이를 위한 기능을 내장하고 있다.

- 로그인 화면(가입·비밀번호 재설정 포함)의 폼 하단, 설정 › 계정과 관리 › 서비스 상태의 최하단, 설치 마법사에 **"소스 코드"** 링크가 있다. 주소는 backend 가 로그인 전에도 조회 가능한 응답(`GET /api/health` 의 `source_url`)으로 제공한다.
- 기본 주소는 이 프로젝트의 소스 리포다. **수정본으로 서비스를 제공하는 경우** `.env` 의 `JW_SOURCE_URL` 을 **수정된 소스 코드를 받을 수 있는 주소**로 변경한다([CONFIG.md](CONFIG.md)). 설치 관리자로 설치한 서버에서는 설치 관리자 컨테이너의 환경변수 `JW_SOURCE_URL` 로 지정한다.
- 링크를 삭제하거나 숨기는 수정은 13조의 요구를 다른 방법으로 충족하지 않는 한 라이선스 위반에 해당할 수 있다.

수정 없이 배포본 그대로 운영하는 경우 13조의 요구 범위는 해석이 갈릴 수 있으나, 기본 주소가 해당 버전의 소스를 가리키므로 링크를 유지하는 것으로 충분하다. 리포의 태그(`v<버전>`)가 해당 버전의 소스다.

## 3. 외부 이미지(재배포하지 않음)

| 이미지 | 라이선스 | 사용 구역 |
|---|---|---|
| PostgreSQL | PostgreSQL License | 기본 |
| Redis 8.8 | RSALv2 / SSPLv1 / AGPL-3.0 삼중(이용자가 택일) | 기본 |
| nginx | BSD-2-Clause | 기본 |
| certbot | Apache-2.0 | 기본(인증서 자동 발급 사용 시) |
| Gitea | MIT | 코드 저장소 구역 |
| LiveKit server · egress | Apache-2.0 | 회의 구역 |
| OnlyOffice Document Server | **AGPL-3.0** | 문서 편집 구역 |
| SearXNG | **AGPL-3.0** | AI 도우미 구역 |
| kasmweb/chromium | 레시피 MIT · 내장 KasmVNC **GPL-2.0** | 격리 브라우저 |

사실:

- 위 이미지는 본 프로젝트의 레지스트리에 게시하지 않는다. `docker-compose.yml` 에 **원 배포처의 주소와 다이제스트(digest)**를 명시하며, 설치 관리자가 원 배포처에서 직접 pull 한다. 릴리스 목록 파일(manifest)에도 원 배포처의 `저장소@sha256:…` 를 기록한다([releases.md](releases.md)). kasmweb/chromium 만 compose 에 포함되지 않으며, backend 가 세션마다 태그로 pull 해 기동한다.
- 수정하지 않는다. 설정 파일과 환경 변수만 주입한다.
- 본 프로젝트 코드와는 네트워크(HTTP·WOPI·Redis 프로토콜 등)로만 통신하는 별도 프로세스다. 각 이미지에는 자체 라이선스가 그대로 적용되며, 본 프로젝트 코드의 AGPL 이 이들에 전이되지 않고 이들의 라이선스도 본 프로젝트 코드에 전이되지 않는다는 해석이 일반적이다.
- **예외 — 오프라인 번들.** `jwrelease bundle` 에 `--include-third-party` 를 지정하면 외부 이미지를 `docker save` 한 파일이 번들에 포함된다([releases.md](releases.md)의 "오프라인 묶음"). 이렇게 생성한 번들을 게시하면 외부 이미지를 **본 프로젝트가 재배포**하는 것이 된다. 옵션을 지정하지 않으면 자체 빌드 이미지만 포함된다.
- **예외 — 메일 서버.** `mailserver` 는 외부 이미지가 아니라 docker-mailserver 에 보안 업데이트를 적용해 본 프로젝트 명의로 재배포하는 파생 이미지다. 5절에서 다룬다.

해석:

- 원 배포처에서 수정 없이 pull 해 실행하는 한, 해당 이미지의 배포자는 원 배포처이고 운영자는 이용자다. 각 라이선스의 배포 시 의무는 통상 운영자에게 발생하지 않는다.
- OnlyOffice 와 SearXNG 도 AGPL 이다. 운영자가 **해당 이미지를 수정해** 서비스를 제공하면 그 수정본의 소스 코드를 이용자에게 제공해야 한다. 수정 없이 원 이미지로 실행하는 경우 추가 의무는 없다는 해석이 일반적이다.
- Redis 는 세 라이선스 중 하나를 선택하여 적용한다. RSALv2 와 SSPLv1 은 Redis 자체를 관리형 서비스로 제3자에게 판매하는 경우를 제한한다. 워크스페이스의 내부 저장소로 사용하는 것은 이에 해당하지 않는다는 해석이 일반적이다.

## 4. 플러그인

플러그인에 대한 예외는 두지 않는다.

- backend 플러그인은 backend 와 **동일 프로세스**에서 실행되며 backend 의 코드(`app.*`, 플러그인 SDK)를 호출한다. 프런트 플러그인도 호스트 화면의 모듈을 호출한다. 이와 같이 프로그램의 코드를 호출하는 플러그인은 프로그램과 결합된 저작물이 되므로, **배포하는 경우 AGPL-3.0 과 호환되는 조건으로 배포해야 한다는 것이 일반적인 해석**이다.
- 자체 서버에만 설치해 사용하고 타인에게 양도하지 않는 플러그인은 배포에 해당하지 않는다. 다만 해당 서버를 타인이 네트워크로 이용한다면, 플러그인을 설치한 판이 "수정본"에 해당하는지(13조)는 플러그인과 프로그램의 결합 정도에 따라 달라지는 문제이며 이 문서에서는 단정하지 않는다. 확실히 하려면 해당 플러그인의 소스도 `JW_SOURCE_URL` 이 가리키는 위치에서 받을 수 있도록 한다.
- HTTP·MCP 등 공개 프로토콜로만 이 서버와 통신하는 **별도 프로그램**(다른 서버의 서비스, 외부 MCP 클라이언트 등)은 플러그인이 아니며, 이 조건의 적용 대상이 아니라는 해석이 일반적이다.

## 5. 자체 빌드 이미지에 포함해 배포하는 제3자 구성 요소

**이미지를 레지스트리에 게시해 타인이 pull 할 수 있게 하는 것 자체가 배포다.** 수정하지 않았더라도 GPL·LGPL 프로그램의 바이너리를 제공하면 해당 라이선스의 배포 조건이 적용된다.

|---|---|---|---|

자체 빌드 이미지는 모두 `/licenses/` 에 `LICENSE`(AGPL 전문), `NOTICE`, `THIRD_PARTY_LICENSES.md` 를 포함한다(rbi-mirror 는 `THIRD_PARTY-rbi-mirror.md` 도 포함).

### 5.2 aioimaplib(GPL-3.0-only)과 backend

사실: backend 는 aioimaplib 을 동일 프로세스에서 `import` 해 호출한다. aioimaplib 은 수정하지 않고 PyPI 배포본을 그대로 설치한다.

- 파이썬 `import` 로 GPL 라이브러리를 사용하는 프로그램은 해당 라이브러리와 결합 저작물을 구성한다고 보는 것이 자유 소프트웨어 재단을 비롯한 다수의 해석이다.
- GPL 버전 3 의 13조와 AGPL 버전 3 의 13조는 **두 라이선스의 저작물을 하나로 결합해 배포하는 것을 상호 허용**한다. 결합물에서 GPL 부분에는 GPL-3.0 이, 본 프로젝트 부분에는 AGPL-3.0 이 그대로 적용되며, 네트워크 조항(AGPL 13조)은 결합물 전체에 적용된다고 두 조문이 규정한다.
- 따라서 AGPL-3.0-or-later 인 backend 가 GPL-3.0-only 인 aioimaplib 을 포함해 배포되는 것은 두 라이선스가 예정한 경우다. aioimaplib 이 "3.0 한정"이므로 결합물은 사실상 버전 3 의 조건으로 취급된다.
- 배포자의 의무는 5.3 과 같다: aioimaplib 의 라이선스 전문·고지 제공과 소스 제공 방법의 안내.

### 5.3 GPL 프로그램을 이미지에 포함해 배포할 때의 의무

GPL-2.0·GPL-3.0 프로그램의 바이너리를 배포하는 경우 수정 여부와 관계없이 다음이 요구된다.

- 수령자에게 **해당 프로그램의 라이선스 전문**을 함께 제공한다.
- **해당 프로그램의 소스**를 함께 제공하거나 입수 방법을 제공한다(GPL-2.0 은 3년간 유효한 서면 제공 약정, GPL-3.0 은 동일 위치에서의 다운로드 제공 등).
- 저작권 고지와 무보증 고지를 삭제하지 않는다.

데비안 패키지로 설치한 구성 요소는 이미지 내 `/usr/share/doc/<패키지>/copyright` 에 고지가 유지되며 소스는 데비안이 공개한다. pip 로 설치한 구성 요소는 `site-packages` 의 `*.dist-info` 에 라이선스 파일이 유지된다. 다만 **"상위 배포처가 공개하고 있다"는 사실만으로 배포자의 소스 제공 의무가 충족되는지는 판단이 필요하다** — 6절.

별도 프로세스로 실행만 하는 GPL 프로그램(pandoc, iptables, LibreOffice 확장 등)은 동일 이미지에 포함되어 있더라도 본 프로젝트 코드의 라이선스에 영향을 주지 않는다는 해석이 일반적이다(GPL 의 "단순 집합").

### 5.4 LGPL 라이브러리 (ldap3, psycopg, libvips)

LGPL 은 라이브러리를 **사용하는** 프로그램에 자신의 조건을 요구하지 않는다. 대신 배포자에게 다음을 요구한다.

- 라이브러리의 라이선스 전문과 저작권 고지를 함께 제공한다.
- 라이브러리의 소스를 입수할 수 있도록 한다.
- 수령자가 **라이브러리를 수정본으로 교체할 수 있어야** 한다.

파이썬 패키지는 소스 형태(`site-packages` 의 `.py`)로 설치되어 교체가 가능하며, `psycopg-binary` 는 `psycopg` 순수 파이썬 구현이나 재빌드한 휠로 대체할 수 있다. libvips 는 sharp 가 별도 공유 라이브러리로 로드한다. 따라서 교체 가능성 조건은 충족된다는 해석이 일반적이다. 고지와 소스 제공은 배포자가 별도로 이행해야 한다.

### 5.5 MPL-2.0 (pywebpush, py-vapid, certifi, LibreOffice, dompurify)

파일 단위 카피레프트다. MPL 파일을 **수정해** 배포하면 해당 파일의 소스를 공개해야 한다. 수정 없이 사용하는 경우 라이선스 고지와 소스 위치 안내로 충분하다. MPL-2.0 은 GPL·AGPL 계열과의 결합 배포를 허용하는 조항(보조 라이선스)을 두고 있다. dompurify 는 Apache-2.0 을 선택할 수 있다.

### 5.6 mailserver 이미지

`mailserver/image/Dockerfile` 은 docker-mailserver 원 이미지에서 `apt-get install --only-upgrade` 만 실행한다. 프로그램을 수정하지는 않으나 결과물은 **본 프로젝트가 배포하는 이미지**다. 이미지에 포함된 GPL 프로그램(ClamAV 등)에 대해 5.3 의 의무가 본 프로젝트에 발생한다. 원 이미지를 그대로 pull 하게 하는 다른 외부 이미지와의 차이점이다.

### 5.7 비오픈소스 의존성

웹·서버 이미지에는 비오픈소스 의존성이 없다. AGPL 프로그램에 그러한 구성 요소를 결합해 배포할 수 없으므로 포함하지 않는 것을 원칙으로 한다([CONTRIBUTING.md](../CONTRIBUTING.md)).

모바일 앱의 Android 푸시(Firebase·Google Play 서비스)와 Android SDK 에는 Google 약관이 적용되는 비오픈소스 부분이 있다. `google-services.json` 을 포함해 빌드하는 경우에만 해당한다 — 그렇게 빌드한 앱의 **배포** 가능 여부는 6절의 확인 사항이다.

## 6. 배포 전 확인 필요

이미지를 공개 레지스트리에 게시하기 전에 담당자가 결정 또는 확인해야 하는 사항이다. 현재 리포에는 아래 항목을 처리하는 수단이 없다.

1. **이미지 내 고지의 충분성.** `/licenses/` 에는 본 프로젝트의 라이선스 전문과 제3자 **목록**이 포함된다. `THIRD_PARTY_LICENSES.md` 는 목록이며 **제3자 라이선스 전문 모음이 아니고**, 웹 번들(frontend-react)은 빌드 과정에서 라이선스 주석이 제거될 수 있다. MIT·BSD·Apache-2.0·ISC·OFL 도 저작권 고지와 라이선스 전문의 동봉을 요구하므로, 전문까지 이미지에 포함할지 결정해야 한다.
2. **GPL·LGPL 구성 요소의 소스 제공 방법.** 대상: aioimaplib, ldap3, psycopg, H2Orestart, pandoc, iptables·iproute2·procps, libvips, OpenJDK, mailserver 이미지 내 GPL 프로그램, 베이스 OS. 상위 배포처(PyPI·데비안·GitHub) 주소 안내로 충분한지, 해당 버전의 소스를 직접 보관·제공해야 하는지, 서면 제공 약정을 둘지 결정해야 한다.
3. **본 프로젝트 소스의 "해당 소스" 범위.** AGPL 은 실행물 생성에 필요한 스크립트까지 소스로 본다. Dockerfile·compose·빌드 워크플로는 리포에 있다. 릴리스마다 태그(`v<버전>`)를 생성해 배포한 이미지와 소스가 대응되도록 한다.
4. **H2Orestart(GPL-3.0)의 docconv 이미지 포함 배포 여부.** 빌드 인자 `H2ORESTART_VERSION` 을 비우면 포함하지 않고 빌드된다(HWP 변환 기능은 제외된다).
5. **오프라인 번들의 외부 이미지 포함 여부.** 포함하면 OnlyOffice·SearXNG(AGPL-3.0), Redis(삼중 라이선스), kasmweb/chromium(GPL-2.0 인 KasmVNC 포함) 등을 본 프로젝트가 재배포하는 것이 되며, 각 라이선스의 배포 의무와 상표 사용 조건이 본 프로젝트에 발생한다.
6. **mailserver 파생 이미지.** 원 이미지를 그대로 pull 하게 하고 보안 업데이트는 다른 방법으로 적용할지, 파생 이미지 배포를 유지하면서 2번을 처리할지.
7. **버전이 고정되지 않은 데비안 패키지.** pandoc, LibreOffice 등은 빌드 시점의 버전이 설치되므로, 배포한 이미지에 포함된 정확한 버전(소스 제공의 기준)을 빌드 시 기록할 필요가 있다.
8. **아이콘 고지.** `frontend-react/src/utils/icons.ts` 에 Lucide(ISC)에서 가져온 SVG 경로가 있다. ISC 는 저작권 고지 유지를 요구한다.
9. **데스크톱·모바일 앱.** Electron 설치 파일에는 Chromium 과 FFmpeg(LGPL-2.1+)이 포함된다. 설치 파일에 본 프로젝트의 라이선스와 제3자 고지를 포함하는지, 앱 내에서 소스 주소를 표시하는지, 앱 스토어 약관이 AGPL 배포와 양립하는지, 푸시용 비오픈소스 구성 요소를 포함한 빌드의 배포가 가능한지 확인한다.
10. **기여 조건의 문안과 동의 기록.** 기여 조건(재허가 권한 포함)은 CONTRIBUTING.md 의 한 절이며, 동의는 PR 템플릿의 확인란으로 받는다. 문안이 의도한 효력을 갖는지, 확인란 표시가 동의 기록으로서 충분한지 확인한다. 이 조건의 도입 전에 접수한 외부 기여가 있다면 별도로 동의를 받아야 한다.

## 7. 운영자 유의 사항

- pull 한 이미지를 **수정 없이 자체 서버에서 운영**하는 경우 어느 구성 요소에서도 추가 의무가 발생하지 않는다는 해석이 일반적이다. "소스 코드" 링크는 유지한다.
- **수정본으로 서비스를 제공하는 경우** 수정된 소스 코드를 이용자가 받을 수 있도록 하고 `JW_SOURCE_URL` 을 해당 주소로 변경한다(2절).
- 이미지를 수정하거나 재빌드해 **타인에게 배포하는 경우** 1절과 5절이 그 배포자에게 동일하게 적용된다 — AGPL 로, 소스와 함께.
- AGPL 이미지(OnlyOffice, SearXNG)를 **수정해** 이용자에게 서비스를 제공하는 경우 해당 수정본의 소스도 이용자에게 제공해야 한다.
