# 운영 안내

본 문서는 설치 후 서버를 운영하는 관리자를 대상으로 한다. 대부분의 작업은 관리 화면에서 수행한다. 화면 이름은 "관리 › 구역"과 같이 표기한다 — 관리자 계정으로 로그인한 후 관리 메뉴의 해당 항목을 의미한다.

- 설치: [install.md](install.md). 용어 정의: [glossary.md](glossary.md).
- 본 문서는 **설치 관리자로 설치한 서버**를 기준으로 한다. 설치 관리자 없이 직접 기동한 서버에서는 관리 › 구역·업데이트와 인증서 카드가 읽기 전용이거나 "여기서 할 수 없습니다"로 표시된다 — 해당 경우의 절차는 [deployment.md](deployment.md).
- 설치 관리자 컨테이너(`jw-installer`)는 설치 완료 후에도 **상시 실행 상태를 유지해야 한다.** 구역 활성화·비활성화, 업데이트, 인증서 재발급 및 갱신 후속 처리를 이 컨테이너가 담당한다.

## 1. 구역 활성화 및 비활성화

관리 › 구역. 상단에 권장 메모리 합계가 표시되며, 구역과 선택 애드온마다 스위치가 있다.

**활성화.** 스위치를 선택하면 대화 상자가 표시된다. 설정이 필요한 구역(메일·회의·AI 도우미·코드 저장소)은 설정을 먼저 입력받고, 이어서 메모리와 신규 개방 포트를 확인한 후 활성화한다. 진행은 3단계다: 받기 → 설정 → 워크스페이스와 연결.

- 권장 메모리 합계가 서버 메모리를 초과하면 활성화할 수 없다.
- "열 포트"에 표시된 포트는 공유기 또는 방화벽에서 관리자가 직접 개방해야 한다. 화면은 개방 여부를 검증하지 않는다.
- 외부 이미지(문서 편집기, 회의 서버, 코드 저장소 등)는 활성화 시점에 원 배포처에서 직접 pull 한다. 서버의 아웃바운드 인터넷 연결이 필요하다.
- 실패하면 해당 구역은 **비활성화 상태**로 복귀하며 다른 구역은 정상 동작한다. "기록 보기"로 원인을 확인한 후 재시도한다.

**비활성화.** 메뉴에서 해당 구역의 화면이 제거되고 컨테이너가 중지된다. **데이터는 삭제되지 않는다** — 재활성화하면 기존 데이터가 그대로 표시된다.

**설정 변경.** 활성화된 구역의 "설정"에서 변경한다(메일 방식, 회의의 중계·무손실 오디오, AI 제공자, 코드 저장소 버전). 적용에 실패하면 이전 값으로 복원한다.

**연동 보류.** 코드 저장소 구역에 "연동 보류"가 표시되면 로그인 연동이 보류된 상태다. 접속 주소의 인증서가 임시 인증서(또는 코드 저장소가 신뢰하지 않는 사설 인증서)인 경우에 발생한다. 신뢰되는 인증서로 교체한 후([5절](#5-인증서)) "다시 연결"을 선택한다.

구역을 활성화·비활성화하는 동안 서버(backend)가 1회 재시작된다. 화면에 일시적으로 "다시 연결 중"이 표시된다.

## 2. 업데이트

관리 › 업데이트. 탭은 현황 · 설정 · 롤백 · 앱 배포 · 기록 · 오프라인 업데이트로 구성된다. 동작의 상세는 [update-system.md](update-system.md).

### 수동 업데이트 (기본)

1. 설치 관리자가 6시간마다 새 버전을 확인한다. 수신만 수행하며, 서버의 식별자나 통계를 전송하지 않는다.
2. 새 버전이 있으면 **현황**에 표시된다. 내용을 확인한 후 "업데이트 시작"을 선택한다.
3. 전체 사용자의 화면에 5분간 사전 공지 배너가 표시된다("지금 바로 시작"·"취소" 가능). 사전 공지가 종료되면 점검 모드로 전환되며 일반 사용자에게는 점검 화면이 표시된다.
4. 사전 점검 → 자동 백업(DB·설정) → 이미지 pull → DB 변경 → 구역 교체 → 상태 확인 순으로 진행한다. 설치 관리자 자신도 새 버전으로 교체된다.
5. 완료되면 점검 모드가 해제되고 **기록**에 남는다.

### 자동 업데이트

**설정**에서 적용 방식을 "자동"으로 변경한다. 지정한 시간대(기본 03:00~05:00, 서버 시간)에 **공개 후 3일이 경과한 릴리스만** 적용한다. 시작 5분 전에 사전 공지가 표시된다. 실패하면 롤백하고 자동 업데이트를 중단한다 — 현황의 "자동 업데이트 다시 활성화"를 선택해야 재시도한다.

### 채널

**설정**의 채널: 안정판(Stable, 기본) 또는 시험판(Beta). Beta 는 검증이 완료되지 않은 버전이다. Beta 로 최초 전환하기 직전의 백업은 별도로 보관된다. Stable 로 복귀할 때는 다음 중 하나를 선택한다.

- **기다리기** — Stable 이 현재 버전에 도달할 때까지 현 상태로 사용한다(버전을 낮추지 않는다).
- **시험판 이전 상태로 복원** — Beta 로 전환하기 직전의 백업으로 복원한다. 복원 범위는 아래 복원 지점과 동일하다.

### 실패 시 동작과 롤백

| 실패 시점 | 동작 |
|---|---|
| DB 변경 전(사전 점검·백업·이미지 pull) | 중단 후 관리자의 선택을 대기한다: "이 단계부터 다시" 또는 "되돌리기" |
| DB 변경 이후 | 확인 없이 이전 버전으로 롤백한다(이전 이미지 + 직전 백업의 DB) |
| 롤백도 실패 | 점검 모드에서 중단된다. 화면에 중단된 단계와 백업의 위치가 표시된다. "다시 시도"가 가능하며, 수동 절차는 [data-safety.md](data-safety.md) 4절 |

업데이트마다 생성되는 백업이 **복원 지점**이다. 최근 3개를 보관하며, **롤백** 탭에서 선택해 해당 버전·해당 시점의 DB 로 복원할 수 있다. 복원 지점의 범위는 다음과 같다.

| 구분 | 대상 |
|---|---|
| 복원 지점 시점으로 되돌림 | 워크스페이스 데이터베이스(대화·일정·연락처·할 일·게시판·위키·계정·관리 설정 등), 스택 설정(`.env` 의 비밀값·암호화 키 포함) |
| 유지(되돌리지 않음) | 파일 저장소, 메일 서버의 메일함(받은 메일·보낸 메일), 코드 저장소(Gitea), 플러그인 데이터 |

복원 지점 이후에 생성·변경한 데이터베이스의 내용은 소실된다. 유지 대상은 복원 지점 이후의 내용이 그대로 남는다 — 예: 복원 지점 이후에 수신한 메일은 메일함에 남는다.

### 오프라인 업데이트 (인터넷 미연결 서버)

1. 인터넷에 연결된 PC 에서 해당 버전의 오프라인 번들(`just-workspace-<버전>-offline.tar`)을 다운로드한다.
2. **오프라인 업데이트** 탭에서 업로드하거나, 서버의 설치 폴더 하위로 복사한 후 해당 경로를 입력한다(대용량 파일은 경로 방식을 권장한다 — 이어 올리기를 지원하지 않는다).
3. 서명과 버전의 검증이 완료되면 추가로 필요한 외부 이미지(데이터베이스·웹 서버 등)의 목록과, 이를 PC 에서 파일로 저장하는 명령이 표시된다.
4. 누락된 이미지 파일을 업로드하면 적용할 수 있다. 이후 절차는 온라인 업데이트와 동일하다.

### "업데이트 확인이 구성되지 않았습니다"

릴리스의 서명을 검증할 공개 키가 설치 관리자에 없음을 의미한다. 공개 키 폴더(`installer/keys/`)를 비운 상태로 빌드한 설치 관리자가 이에 해당한다. 사용할 채널의 공개 키와 주소를 서버 터미널에서 등록한다. 공식 채널 이외의 채널을 사용하는 경우에도 동일한 명령을 사용한다.

```bash
docker exec -i jw-installer jw update-key add - < release.pub     # 공개 키(검증 후 <설치 폴더>/state/update/keys/ 에 저장한다)
docker exec jw-installer jw update-channel https://releases.example.com   # 채널 주소(공식 채널 사용 시 생략)
docker exec jw-installer jw update-key                            # 현재 사용 중인 키와 지문
```

- 키를 등록하면 해당 지문이 출력된다 — 릴리스 배포자가 고지한 지문과 일치하는지 확인한다. 비공개 키는 등록할 수 없다.
- 공개 키는 최대 2개(현재·다음)까지 보관한다. 설치 폴더에 키가 있으면 이미지에 포함된 키는 사용하지 않는다. 삭제는 `jw update-key remove <이름>`.
- 채널 주소를 변경하면 이전 채널에서 캐시한 확인 결과를 삭제한다. `jw update-channel --reset` 은 기본값(환경변수 `JW_UPDATE_CHANNEL_URL` 또는 이미지의 값)으로 복원한다.
- 등록 후 관리 › 업데이트에서 "지금 확인"을 선택한다(자동 확인 주기는 6시간). 채널을 자체 구성하는 방법은 [releases.md](releases.md), 구조는 [installer.md](installer.md) 16절.

채널 없이 소스에서 빌드해 운영하는 서버를 새 버전으로 업데이트하는 화면상의 절차는 현재 제공되지 않는다. 전체 백업을 생성하고, 새 버전으로 재설치한 후 "백업에서 복원"으로 복원하는 방법을 사용한다([3절](#3-백업-복원-및-서버-이전)). 복원은 백업과 동일하거나 상위인 버전에서만 가능하다.

## 3. 백업, 복원 및 서버 이전

형식과 세부 규칙은 [data-safety.md](data-safety.md).

### 백업 생성

관리 › 저장소·백업의 백업 카드.

- **지금 백업** — 전체 백업을 생성한다. 코드 저장소는 백업 중 일시 중지된다.
- **예약 백업 (매일)** — 시각과 보존 일수를 지정한다.
- 목록의 **받기** — 백업을 단일 파일(`.jwbak`)로 다운로드한다.

터미널에서도 동일한 형식으로 생성할 수 있다.

```bash
docker exec ws-backend python -m app.cli backup create --kind full --include-files --pack
docker exec ws-backend python -m app.cli backup list
```

유의 사항:

- **백업은 서버 외부에도 보관한다.** 관리 화면의 백업은 서버의 백업 볼륨(`ws-backups`)에 저장된다. 서버의 디스크에 장애가 발생하면 함께 소실된다.
- **백업 파일에는 암호화 키와 비밀번호가 포함된다.** 이 파일의 보유자는 서버의 모든 데이터를 열람할 수 있다. 접근이 통제된 위치에 보관한다. 설정 항목은 암호로 보호할 수 있다(`--password-file`).
- **포함 항목**: 데이터베이스, 설정(`.env` — 암호화 키), 메일, 코드 저장소, 플러그인 데이터, 인증서, 앱 서명 키, 그리고 (로컬 저장소인 경우, 선택) 파일.
- **제외 항목**: 로그인 세션(복원 후 전원 재로그인), **NFS 의 파일**(NAS 측의 스냅숏·복제로 별도 보호한다), 설치한 플러그인의 코드, 컨테이너 이미지, 로그.

### 서버 이전 · 백업에서 복원

1. 기존 서버에서 전체 백업을 생성해 다운로드한다. 파일 저장 위치가 이 서버의 디스크인 경우 파일을 포함해 생성한다.
2. 신규 서버에서 설치 관리자를 기동하고([install.md](install.md)), 시작 방식에서 **백업에서 복원**을 선택한다.
3. 백업 파일을 업로드하거나, 서버에 미리 복사해 둔 파일의 경로를 지정한다(대용량 백업은 경로 방식을 권장한다).
4. 내용(생성 서버, 버전, 구역, 파일 포함 여부)을 확인하고, 신규 서버에서 재지정이 필요한 항목만 지정한다 — 접속 주소, 연결 형태, 인증서, 파일 저장 위치. 구역·메일·관리자 계정은 백업의 값을 사용한다.
5. 완료되면 접속 주소의 DNS 레코드를 신규 서버로 변경하고, 임시 인증서인 경우 인증서를 발급하며, 검증 후 **기존 서버를 중지한다**(두 서버를 병행 운영하면 데이터가 분기된다).

- 백업의 버전이 설치 관리자의 버전보다 **높으면** 복원할 수 없다. 동일하거나 낮으면 복원 후 버전 차이를 마이그레이션한다.
- 기존 저장소가 NFS 인 경우 동일한 공유를 다시 연결한다. 파일은 백업이 아니라 해당 공유에 있다.
- 설정이 암호로 보호된 백업은 암호 입력을 요구한다.
- 무인 설치(응답 파일)로 수행하는 방법과 단계별 설명은 [installer.md](installer.md) 14절.

### 동일 서버에서의 복원

- **업데이트 이전 시점으로** — 관리 › 업데이트 › 롤백의 복원 지점([2절](#2-업데이트)).
- **전체 백업으로** — 앱 내에서는 복원하지 않는다(실행 중인 서버는 자신의 DB 를 교체할 수 없다). 서버 터미널에서 수행한다.

  ```bash
  docker exec jw-installer jw restore --list                       # 백업 볼륨에 있는 백업(관리 화면에서 생성한 것)
  docker exec jw-installer jw restore 20260101_030000-full         # 내용과 복원 대상 항목만 표시한다(변경 사항 없음)
  docker exec jw-installer jw restore 20260101_030000-full --yes   # 복원한다
  docker exec jw-installer jw restore /srv/backups/full.jwbak --yes   # 서버의 다른 위치에 있는 파일은 절대 경로로 지정
  ```

  - 데이터베이스·메일·코드 저장소·플러그인 데이터·인증서·앱 서명 키·(백업에 포함된 경우) 파일을 **백업 시점의 상태로 교체한다.** 백업 이후에 생성된 데이터는 소실된다. 일부 항목만 복원하려면 `--items db,mail`.
  - **설정(`.env`)은 복원하지 않는다** — 구역·버전·접속 주소는 현재 값을 유지한다. 따라서 다른 서버에서 생성한 백업(암호화 키가 상이하다)은 이 명령에서 거부된다. 해당 백업은 재설치하면서 "백업에서 복원"으로 업로드한다([install.md](install.md#재설치)).
  - 실행 중에는 서비스가 중단되며(웹 화면은 점검 중으로 응답한다), 완료 후 전체 사용자가 재로그인해야 한다. 복원 전의 DB 는 백업 볼륨의 `_pre-restore/` 에 덤프해 둔다.
  - 실패하면 중단된 단계, 원인, 이후의 DB 상태를 출력하고 종료 코드 1 로 종료한다. 단계와 실패 시 동작은 [data-safety.md](data-safety.md) 4절.
  - 백업의 버전이 현재 버전보다 높으면 복원할 수 없다.
- 직접 기동한 서버는 `scripts/restore.sh`([deployment.md](deployment.md)).

## 4. 파일 저장소

관리 › 저장소·백업에 저장소 상태(종류, 위치, 연결 상태, 여유 공간)가 표시된다. 종류는 "이 서버의 디스크" 또는 "네트워크 저장소 (NFS)"다.

### 연결 단절 시 동작

저장소가 확인되지 않으면 서버는 **파일 쓰기를 거부한다**(단절된 저장소의 마운트 지점에 남은 빈 폴더에 기록하는 사고를 방지하기 위함이다). 관리 화면에 "파일 저장소와 연결이 끊겨 파일 쓰기가 멈췄습니다"가 표시되며, 사용자는 파일 탭에서 파일을 열거나 업로드할 수 없다. 채팅과 메일 본문은 정상 동작한다.

- NFS: NAS 의 가동 여부와 이 서버와 NAS 간 네트워크 상태를 확인한다.
- 이 서버의 디스크: 저장소 디스크가 서버에 마운트되어 있는지 확인한다.
- 연결이 복구되면 자동으로 재연결된다. "다시 확인"으로 즉시 확인할 수 있다.

| 화면의 사유 | 의미 |
|---|---|
| 저장소 마커를 찾을 수 없습니다 | 저장소가 마운트되지 않았거나 다른(빈) 폴더가 마운트되었다 |
| 다른 설치의 저장소가 마운트되어 있습니다 | 저장소 마커의 설치 id 가 이 서버의 것과 다르다 — 잘못된 공유를 연결했다 |
| 저장소가 응답하지 않습니다 | NFS 서버가 응답하지 않는다 |

알려진 제한 사항: 쓰기 차단의 적용 범위는 파일 탭과 문서 편집의 저장이다. 채팅 첨부와 같이 다른 경로로 저장소에 기록하는 기능에는 아직 적용되지 않는다. NFS 가 단절된 동안 저장소를 읽는 요청은 NFS 가 복구될 때까지 대기한다([installer.md](installer.md) 12절).

### 저장 위치 변경

이 서버의 디스크와 NFS 간 전환을 설치 후에 수행하는 화면은 제공되지 않는다. 전체 백업(파일 포함)을 생성하고 "백업에서 복원"으로 새 위치를 지정하는 것이 문서화된 절차다.

관리 › 저장소·백업의 "파일 저장소 종류"에는 S3 호환 오브젝트 저장소로 전환하는 설정도 있다(전환 이후의 신규 파일부터 해당 저장소에 저장된다). 설치 관리자의 저장소 점검·저장소 마커·검수는 이 서버의 디스크와 NFS 만을 대상으로 한다.

## 5. 인증서

관리 › 보안·SSL 의 **인증서** 카드에 종류, 접속 주소, 만료일, 발급자가 표시된다.

| 종류 | 갱신 |
|---|---|
| 자동 발급 (Let's Encrypt) | 자동 갱신된다. 접속 주소가 계속 이 서버를 가리키고 외부에서 80번으로 접근 가능해야 한다 |
| 올린 인증서 | 만료 전에 새 인증서를 이 카드에서 업로드한다 |
| 임시 인증서 (자체 서명) | 브라우저에 경고가 표시된다. 이 카드에서 발급하거나 업로드한다 |
| 프록시가 처리 | 프런트 프록시에서 발급·갱신한다. 이 화면에서는 변경하지 않는다 |

**재발급 / 교체.** 카드에서 자동 발급을 재요청하거나, 보유한 인증서와 개인 키를 업로드한다. 전환 가능한 방향은 임시 → 자동 발급·업로드, 자동 발급 → 업로드다. 발급에 실패하면 기존 인증서를 유지한다. 성공하면 웹 서버와 회의 서버가 새 인증서를 로드하고, 보류 상태였던 구역 연동(코드 저장소의 로그인 연동)을 재시도한다.

- **사설 CA 가 발급한 인증서**(사내 CA 등)를 업로드하는 경우 해당 **CA 인증서도 함께 제공한다**. 업로드 대화 상자의 "CA 인증서(선택)" 항목에 CA 인증서 파일을 업로드하거나, 인증서 파일 자체에 서버 인증서 다음으로 중간·루트 인증서를 연결한다. 해당 CA 는 이 서버의 코드 저장소(및 backend)의 신뢰 저장소에 추가되므로 코드 저장소의 로그인 연동이 유지된다. 공인 인증 기관의 인증서인 경우 CA 항목은 비워 둔다.
- 서버 인증서 1장만 업로드하면 코드 저장소가 해당 인증서를 신뢰하지 못하여 연동이 보류 상태로 남는다. 이 경우 인증서 카드에 "코드 저장소의 로그인 연동이 보류돼 있습니다"가 표시되고 **[CA 인증서 업로드]** 가 제공된다 — CA 인증서 파일만 업로드하는 것으로 충분하다(인증서와 개인 키는 유지된다). 업로드한 CA 가 해당 인증서의 발급 CA 가 아니면 거부된다.
- 사용자의 브라우저와 기기가 해당 CA 를 신뢰하도록 구성하는 작업은 별도로 수행해야 한다. 문서 편집기가 사설 CA 인증서 환경에서 동작하는지는 검증되지 않았다([installer.md](installer.md) 12절).
- 자동 발급에는 인증서에 포함될 이름(접속 주소, 내장 메일의 `mail.<메일 도메인>`, 회의 중계의 `turn.<접속 주소>`, 격리 브라우저의 `rbi.<접속 주소>`)이 모두 DNS 에 등록되어 있어야 한다.
- 프록시 하단 구성에서는 프록시를 경유하지 않는 이름(메일·회의)에 자체 서명 인증서가 사용된다. 메일 클라이언트에서 인증서 경고가 표시될 수 있다.
- 실제 Let's Encrypt 발급과 갱신은 아직 실서버에서 검증되지 않았다([installer.md](installer.md) 13절).

## 6. 메일 DNS 레코드

내장 메일 서버로 메일을 정상적으로 송수신하려면 메일 도메인에 레코드 5개가 필요하다. 관리 › 구역에서 메일의 "설정"을 열면 **등록할 값과 현재 상태**(확인됨 · 아직 없음 · 값이 다름 · 확인 불가)가 표시되며, 값을 복사할 수 있다.

| 종류 | 이름 | 용도 |
|---|---|---|
| MX | 메일 도메인 | 해당 도메인의 메일을 수신할 서버 |
| A | `mail.<메일 도메인>` | 메일 서버의 주소 |
| TXT (SPF) | 메일 도메인 | 해당 도메인으로 발신이 허용된 서버 |
| TXT (DKIM) | 화면에 표시된 이름 | 발신 메일의 서명 검증용 공개 키(설치 시 생성한 키) |
| TXT (DMARC) | `_dmarc.<메일 도메인>` | 위 두 항목의 검증 실패 시 처리 정책 |

- 레코드가 누락되면 발신 메일이 스팸으로 분류될 수 있다.
- 외부에서 이 서버의 25번 포트로 접근 가능해야 메일을 수신한다. 통신사가 25번을 차단하는 회선에서는 외부 발신 서버로 전환한다.
- 수신 측 서버가 발신 서버의 역방향 이름(PTR)을 확인하는 경우가 많다. PTR 은 서버 임대 사업자(클라우드·통신사)에서 설정한다.
- 서버를 이전하더라도 DKIM 키는 백업에 포함되어 이전된다 — 등록된 레코드를 그대로 사용한다.

## 7. 로그

컨테이너 이름은 `ws-` 로 시작한다. 설치 관리자는 `jw-installer`.

```bash
docker ps --format '{{.Names}}\t{{.Status}}'      # 실행 중인 컨테이너
docker logs --tail 200 ws-backend                 # 서버(API)
docker logs --tail 200 ws-nginx                   # 웹 진입점
docker logs -f ws-mailserver                      # 메일 서버(실시간 추적)
docker logs jw-installer                          # 설치 관리자
```

| 컨테이너 | 역할 |
|---|---|
| `ws-nginx` · `ws-frontend-react` · `ws-backend` | 웹 진입점 · 화면 · 서버(API) |
| `ws-postgres` · `ws-redis` | 데이터베이스 · 캐시 |
| `ws-certbot` | 인증서 자동 발급·갱신 |
| `ws-mailserver` | 메일 구역(내장 메일 서버) |
| `ws-onlyoffice` | 문서 편집 구역 |
| `ws-livekit` · `ws-egress` · `ws-audiorelay` | 회의 구역(회의 서버 · 녹화 · 무손실 오디오) |
| `ws-gitea` | 코드 저장소 구역 |
| `ws-searxng` · `ws-docconv` · `ws-sandbox` | AI 도우미 구역(웹 검색 · 문서 변환 · 코드 실행) |
| `ws-sso` · `ws-ldap` | SSO·LDAP 제공 애드온 |
| `ws-rbi-netfilter` | 격리 브라우저 애드온 |

- **로그 로테이션**: 컨테이너 로그는 서비스당 10 MB 파일 5개까지 보관한다(compose 에 정의되어 있다). 초과분은 오래된 순으로 삭제된다.
- **설치·구역·업데이트의 기록**: 설치 단계는 `<설치 폴더>/state/logs/<단계>.log`, 구역 작업은 관리 › 구역의 "기록 보기", 업데이트는 관리 › 업데이트 › 기록(다운로드 가능).
- **요청 번호**: 사용자의 오류 화면에 "요청 번호"가 표시되면 해당 값으로 서버 로그를 검색한다 — `docker logs ws-backend 2>&1 | grep <요청 번호>`.
- **접근 로그·감사**: 관리 › 접근 로그.
- **서비스 상태**: 관리 › 서비스 상태.

버그 신고 시에는 관련 컨테이너 로그의 마지막 부분을 첨부한다. 로그에 주소·계정 이름 등이 포함될 수 있으므로 게시 전에 확인한다.

## 8. 디스크

```bash
df -h                       # 디스크
docker system df -v         # 이미지·볼륨의 사용 공간
```

| 볼륨 | 내용 |
|---|---|
| `ws-storage-data` | 파일 저장소(이 서버의 디스크를 선택한 경우) |
| `ws-postgres-data` | 데이터베이스 |
| `ws-mail-data` · `ws-mail-state` · `ws-mail-logs` | 메일함 · 메일 상태 · 메일 로그 |
| `ws-gitea-data` | 코드 저장소 |
| `ws-backups` | 관리 화면의 백업과 업데이트 직전 백업 |
| `ws-egress-out` | 회의 녹화의 임시 출력 |
| `ws-certbot-data` | 인증서 |
| `ws-plugins-data` | 업로드해 설치한 플러그인 |

- **백업 볼륨의 사용량 증가가 가장 빠르다.** 예약 백업의 보존 일수를 지정하고, 다운로드해 외부로 이관한 백업은 목록에서 삭제한다.
- **사용자별 할당량과 휴지통 보관 기간**은 관리 › 저장소·백업에서 지정한다.
- **`docker image prune -a` 사용에 주의한다.** 복원 지점으로 복원하려면 해당 버전의 이미지가 서버에 남아 있어야 한다. 업데이트가 성공하면 미사용 상태가 된 이전 이미지는 설치 관리자가 자동으로 정리한다.
- 볼륨은 삭제하지 않는다(`docker volume rm`, `docker compose down -v`, `docker system prune --volumes`). 데이터가 소실된다.

## 9. 문제 해결

| 증상 | 확인 사항 |
|---|---|
| 관리 › 구역·업데이트에 "설치 관리자에 연결하지 못했습니다" | `docker ps` 에 `jw-installer` 가 있는지 확인한다. 중지 상태이면 `docker start jw-installer` |
| 파일을 업로드하거나 열 수 없다 | [4절](#4-파일-저장소) — 저장소 연결 |
| 점검 화면이 해제되지 않는다 | 관리 › 업데이트. 관리자의 선택을 대기 중이거나 롤백이 중단된 상태다([2절](#2-업데이트)) |
| 브라우저에 인증서 경고가 표시된다 | [5절](#5-인증서) — 임시 인증서이거나 만료되었다 |
| 발신 메일이 스팸으로 분류된다 / 메일이 수신되지 않는다 | [6절](#6-메일-dns-레코드) — 레코드와 25번 포트 |
| 초대·비밀번호 재설정 메일이 발송되지 않는다 | 메일 구역이 비활성화 상태이면 시스템 메일을 발송할 수 없다. 메일 구역을 활성화하거나 외부 발신 서버를 설정한다 |
| 외부에서 회의에 참가할 수 없다 | 회의 포트(UDP 7882-7892, UDP 3478, TCP 7881)의 외부 접근 가능 여부와 관리 › 구역의 회의 설정에 지정된 공인 주소를 확인한다 |
| 코드 저장소에 "연동 보류" | [1절](#1-구역-활성화-및-비활성화) — 신뢰되는 인증서로 교체한 후 "다시 연결" |
| 관리자 비밀번호 분실 | `docker exec jw-installer jw reset-admin <아이디>`([install.md](install.md#관리자-비밀번호-분실)) |
| 접속 시 "관리자 계정을 준비하는 중입니다" 가 표시된다 | 관리자 계정이 존재하지 않는다. 설치가 진행 중이면 설치 관리자 화면(`https://<서버 주소>:8443`)에서 완료를 대기한다. 설치가 완료된 서버라면(관리자를 전부 삭제한 경우 등) 서버 터미널에서 생성한다: `docker exec -it -u appuser ws-backend python -m app.cli seed-admin --username <아이디>`. 설치 관리자로 설치한 서버에서는 웹에서 최초 관리자를 생성할 수 없다 |
| 최초 설정 화면이 "설정 토큰"을 요구한다 | 직접 기동한 서버다. `docker compose logs backend \| grep "setup token"` 의 최신 값을 입력한다. 재발급: `docker compose exec backend python -m app.cli setup-token`([deployment.md](deployment.md#최초-관리자-계정-생성)) |
| 서버(backend)가 기동하지 않고 로그에 비밀값 이름이 출력된다 | 취약한 비밀값·기본 비밀값으로는 기동하지 않는다. 직접 기동한 설치에서 발생한다 — [CONFIG.md](CONFIG.md)의 "비밀값" |
| 서버가 기동하지 않고 "DB 스키마 버전이 … 높습니다" | DB 가 코드보다 상위 버전이다(이미지만 이전 버전으로 되돌린 경우). [data-safety.md](data-safety.md) 5절 |
| 공유기 하단 서버에서 내부 접속은 가능하나 외부 접속이 불가하다 | 공유기의 포트 포워딩. 필요한 포트는 [install.md](install.md#포트) |
