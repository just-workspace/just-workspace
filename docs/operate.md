# 운영 안내

설치한 뒤 서버를 돌보는 사람을 위한 문서다. 대부분은 관리 화면에서 한다. 화면 이름은 "관리 › 구역"처럼 적는다 — 관리자 계정으로 로그인한 뒤 관리 메뉴의 그 항목이다.

- 설치는 [install.md](install.md), 낱말은 [glossary.md](glossary.md).
- 이 문서는 **설치 관리자로 설치한 서버**가 기준이다. 설치 관리자 없이 직접 띄운 서버는 관리 › 구역·업데이트와 인증서 카드가 읽기 전용이거나 "여기서 할 수 없습니다"로 나온다 — 그 경우의 절차는 [deployment.md](deployment.md).
- 설치 관리자 컨테이너(`jw-installer`)는 설치가 끝난 뒤에도 **계속 떠 있어야 한다.** 구역 켜고 끄기, 업데이트, 인증서 다시 발급과 갱신 뒤 처리를 이 컨테이너가 한다.

## 1. 구역 켜고 끄기

관리 › 구역. 위쪽에 권장 메모리 합계가 보이고, 구역과 선택 애드온마다 스위치가 있다.

**켜기.** 스위치를 누르면 창이 뜬다. 설정이 필요한 구역(메일·회의·AI 도우미·코드 저장소)은 설정부터 묻고, 이어서 메모리와 새로 열 포트를 확인한 뒤 켠다. 진행은 세 단계다: 받기 → 설정 → 워크스페이스와 연결.

- 권장 메모리 합계가 서버 메모리를 넘으면 켤 수 없다.
- "열 포트"에 나온 포트는 공유기나 방화벽에서 직접 열어야 한다. 화면이 대신 확인해 주지 않는다.
- 다른 곳에서 만든 구성 요소(문서 편집기, 회의 서버, 코드 저장소 등)는 켤 때 원 배포처에서 받는다. 서버가 인터넷에 나갈 수 있어야 한다.
- 실패하면 그 구역은 **꺼진 채**로 돌아가고 다른 구역은 그대로 동작한다. "기록 보기"로 원인을 본 뒤 다시 시도한다.

**끄기.** 메뉴에서 그 구역의 화면이 사라지고 컨테이너가 멈춘다. **데이터는 지워지지 않는다** — 다시 켜면 그대로 보인다.

**설정 바꾸기.** 켜진 구역의 "설정"에서 바꾼다(메일 방식, 회의의 중계·무손실 오디오, AI 제공자, 코드 저장소 버전). 적용에 실패하면 이전 값으로 되돌린다.

**연결 보류.** 코드 저장소 구역에 "연결 보류"가 보이면 로그인 연동이 미뤄진 것이다. 접속 주소의 인증서가 임시 인증서(또는 코드 저장소가 믿지 못하는 사설 인증서)일 때 생긴다. 신뢰되는 인증서로 바꾼 뒤([5절](#5-인증서)) "다시 연결"을 누른다.

구역을 켜고 끄는 동안 서버(backend)가 한 번 다시 시작한다. 화면에 잠깐 "다시 연결 중"이 보인다.

## 2. 업데이트

관리 › 업데이트. 탭은 현황 · 설정 · 되돌림 · 앱 배포 · 기록 · 오프라인 업데이트다. 무엇이 일어나는지의 자세한 설명은 [update-system.md](update-system.md).

### 수동 업데이트 (기본)

1. 설치 관리자가 여섯 시간마다 새 버전을 확인한다. 받기만 하고, 서버의 식별자나 통계를 보내지 않는다.
2. 새 버전이 있으면 **현황**에 보인다. 내용을 확인하고 "업데이트 시작"을 누른다.
3. 모든 사용자의 화면에 5분 예고 띠가 뜬다("지금 바로 시작"·"취소" 가능). 예고가 끝나면 점검 상태가 되고 일반 사용자는 점검 화면을 본다.
4. 사전 점검 → 자동 백업(DB·설정) → 이미지 받기 → DB 변경 → 구역 교체 → 상태 확인 순으로 진행한다. 설치 관리자 자신도 새 버전으로 바뀐다.
5. 끝나면 점검이 풀리고 **기록**에 남는다.

### 자동 업데이트

**설정**에서 적용 방식을 "자동"으로 바꾼다. 정한 시간대(기본 03:00~05:00, 서버 시간)에, **나온 지 3일이 지난 릴리스만** 적용한다. 시작 5분 전에 예고가 뜬다. 실패하면 되돌리고 자동 업데이트를 멈춘다 — 현황의 "자동 업데이트 다시 켜기"를 눌러야 다시 시도한다.

### 채널

**설정**의 채널: 안정판(Stable, 기본) 또는 시험판(Beta). 시험판은 검증이 끝나지 않은 버전이다. 시험판으로 처음 올리기 직전의 백업은 따로 보관된다. 안정판으로 돌아올 때는 둘 가운데 고른다:

- **기다리기** — 안정판이 지금 버전을 따라올 때까지 그대로 쓴다(버전을 내리지 않는다).
- **시험판 이전 상태로 복원** — 시험판으로 바꾸기 직전의 백업으로 되돌린다. 그 뒤에 쓴 메일·대화·일정은 사라진다.

### 실패했을 때와 되돌림

| 어디서 실패했나 | 어떻게 되나 |
|---|---|
| DB 변경 전(사전 점검·백업·이미지 받기) | 멈추고 묻는다: "이 단계부터 다시" 또는 "되돌리기" |
| DB 변경부터 | 묻지 않고 이전 버전으로 되돌린다(이전 이미지 + 직전 백업의 DB) |
| 되돌림도 실패 | 점검 상태로 멈춘다. 화면에 멈춘 단계와 백업의 위치가 나온다. "다시 시도"가 되고, 손으로 하는 절차는 [data-safety.md](data-safety.md) 4절 |

업데이트할 때마다 뜬 백업이 **복원 지점**이다. 최근 3개를 두며, **되돌림** 탭에서 골라 그 버전·그 시점의 DB 로 돌아갈 수 있다. 되돌리는 것은 데이터베이스·설정·암호화 키이고, **파일은 백업하지도 되돌리지도 않는다.** 복원 지점 이후에 쓴 메일·대화·일정은 사라진다.

### 인터넷이 없는 서버 (오프라인 업데이트)

1. 인터넷이 되는 PC 에서 그 버전의 묶음 파일(`just-workspace-<버전>-offline.tar`)을 받는다.
2. **오프라인 업데이트** 탭에서 올리거나, 서버의 설치 폴더 아래로 옮긴 뒤 그 경로를 적는다(큰 파일은 경로 방식이 낫다 — 이어 올리기가 없다).
3. 서명과 버전을 확인하면, 추가로 필요한 이미지(데이터베이스·웹 서버처럼 다른 곳에서 만든 구성 요소)의 목록과 그것을 PC 에서 파일로 받는 명령이 나온다.
4. 빠진 이미지 파일을 올리면 적용할 수 있다. 이후는 온라인과 같다.

### "업데이트 확인이 구성되지 않았습니다"

릴리스의 서명을 확인할 공개 키가 설치 관리자에 없다는 뜻이다. 소스에서 직접 빌드한 설치 관리자가 그렇다. 쓸 채널의 공개 키와 주소를 서버 터미널에서 넣는다.

```bash
docker exec -i jw-installer jw update-key add - < release.pub     # 공개 키(검증한 뒤 <설치 폴더>/state/update/keys/ 에 둔다)
docker exec jw-installer jw update-channel https://releases.example.com   # 채널 주소(공식 채널을 쓰면 생략)
docker exec jw-installer jw update-key                            # 지금 쓰는 키와 지문
```

- 키를 넣으면 그 지문이 나온다 — 릴리스를 내는 쪽이 알린 지문과 같은지 확인한다. 비공개 키는 받지 않는다.
- 공개 키는 둘까지(현재·다음) 둔다. 설치 폴더에 키가 있으면 이미지에 든 키는 쓰지 않는다. 지울 때는 `jw update-key remove <이름>`.
- 채널 주소를 바꾸면 앞 채널에서 기억해 둔 확인 결과를 지운다. `jw update-channel --reset` 은 기본값(환경변수 `JW_UPDATE_CHANNEL_URL` 또는 이미지의 값)으로 되돌린다.
- 넣은 뒤 관리 › 업데이트에서 "지금 확인"을 누른다(자동 확인은 여섯 시간마다). 채널을 직접 꾸리는 법은 [releases.md](releases.md), 구조는 [installer.md](installer.md) 16절.

채널 없이 소스로 빌드해 쓰는 서버를 새 버전으로 올리는 화면상의 길은 지금 없다. 전체 백업을 만들고, 새 버전으로 다시 설치한 뒤 "백업에서 복원"으로 되돌리는 방법을 쓴다([3절](#3-백업과-복원-서버-이전)). 복원은 백업보다 같거나 새로운 버전에서만 된다.

## 3. 백업과 복원, 서버 이전

형식과 세부 규칙은 [data-safety.md](data-safety.md).

### 백업 만들기

관리 › 저장소·백업의 백업 카드.

- **지금 백업** — 전체 백업을 만든다. 코드 저장소는 백업하는 동안 잠깐 멈춘다.
- **예약 백업 (매일)** — 시각과 보존 일수를 정한다.
- 목록의 **받기** — 백업을 파일 하나(`.jwbak`)로 내려받는다.

터미널에서도 같은 형식으로 만든다.

```bash
docker exec ws-backend python -m app.cli backup create --kind full --include-files --pack
docker exec ws-backend python -m app.cli backup list
```

알아 둘 것:

- **백업은 서버 밖에도 둔다.** 관리 화면의 백업은 서버의 백업 볼륨(`ws-backups`)에 쌓인다. 서버의 디스크가 죽으면 같이 죽는다.
- **백업 파일에는 암호화 키와 비밀번호가 들어 있다.** 이 파일을 가진 사람은 서버의 모든 데이터를 읽을 수 있다. 접근이 제한된 곳에 둔다. 설정 항목은 암호로 보호할 수 있다(`--password-file`).
- **들어가는 것**: 데이터베이스, 설정(`.env` — 암호화 키), 메일, 코드 저장소, 플러그인 데이터, 인증서, 앱 서명 키, 그리고 (로컬 저장소일 때, 선택) 파일.
- **들어가지 않는 것**: 로그인 세션(복원 뒤 모두 다시 로그인), **NFS 의 파일**(NAS 쪽의 스냅숏·복제로 따로 지킨다), 설치한 플러그인의 코드, 컨테이너 이미지, 로그.

### 새 서버로 옮기기 · 백업에서 복원

1. 원래 서버에서 전체 백업을 만들고 내려받는다. 파일 저장 위치가 이 서버의 디스크면 파일을 포함해 만든다.
2. 새 서버에 설치 관리자를 띄우고([install.md](install.md)), 시작 방식에서 **백업에서 복원**을 고른다.
3. 백업 파일을 올리거나, 서버에 미리 옮겨 둔 파일의 경로를 알려 준다(큰 백업은 경로 방식이 낫다).
4. 내용(만든 서버, 버전, 구역, 파일 포함 여부)을 확인하고, 새 서버에서 다시 정할 것만 정한다 — 접속 주소, 연결 형태, 인증서, 파일 저장 위치. 구역·메일·관리자 계정은 백업에서 온다.
5. 끝나면 접속 주소의 DNS 레코드를 새 서버로 옮기고, 임시 인증서였으면 인증서를 발급하고, 확인한 뒤 **원래 서버를 끈다**(두 서버를 같이 쓰면 데이터가 갈라진다).

- 백업의 버전이 설치 관리자의 버전보다 **높으면** 복원할 수 없다. 같거나 낮으면 복원한 뒤 차이를 메운다.
- 원래 저장소가 NFS 였으면 같은 공유를 다시 연결한다. 파일은 백업이 아니라 그 공유에 있다.
- 설정이 암호로 보호된 백업은 암호를 묻는다.
- 무인(답변 파일)으로 하는 법과 단계별 설명은 [installer.md](installer.md) 14절.

### 같은 서버에서 되돌리기

- **업데이트 이전으로** — 관리 › 업데이트 › 되돌림의 복원 지점([2절](#2-업데이트)).
- **전체 백업으로** — 앱 안에서는 복원하지 않는다(실행 중인 서버는 자신의 DB 를 갈아 끼울 수 없다). 서버 터미널에서 한다.

  ```bash
  docker exec jw-installer jw restore --list                       # 백업 볼륨에 있는 백업(관리 화면이 만든 것)
  docker exec jw-installer jw restore 20260101_030000-full         # 내용과 되돌릴 항목만 보여 준다(아무것도 바꾸지 않는다)
  docker exec jw-installer jw restore 20260101_030000-full --yes   # 되돌린다
  docker exec jw-installer jw restore /srv/backups/full.jwbak --yes   # 서버의 다른 곳에 둔 파일은 절대 경로로
  ```

  - 데이터베이스·메일·코드 저장소·플러그인 데이터·인증서·앱 서명 키·(백업에 들어 있으면) 파일을 **백업 시점으로 바꾼다.** 백업 뒤에 생긴 것은 사라진다. 일부만 되돌리려면 `--items db,mail`.
  - **설정(`.env`)은 되돌리지 않는다** — 구역·버전·접속 주소는 지금 그대로다. 그래서 다른 서버에서 만든 백업(암호화 키가 다르다)은 여기서 거부된다. 그런 백업은 새로 설치하면서 "백업에서 복원"으로 올린다([install.md](install.md#처음부터-다시-설치)).
  - 도는 동안 서비스가 멈추고(웹 화면은 점검 중으로 답한다), 끝나면 모든 사용자가 다시 로그인한다. 복원 전의 DB 는 백업 볼륨의 `_pre-restore/` 에 떠 둔다.
  - 실패하면 어느 단계에서 왜 멈췄는지와 그 뒤의 DB 상태를 알려 주고 종료 코드 1 로 끝난다. 단계와 실패 시 동작은 [data-safety.md](data-safety.md) 4절.
  - 백업의 버전이 지금 버전보다 높으면 되돌릴 수 없다.
- 직접 띄운 서버는 `scripts/restore.sh`([deployment.md](deployment.md)).

## 4. 파일 저장소

관리 › 저장소·백업에 저장소 상태(종류, 위치, 연결 상태, 여유 공간)가 보인다. 종류는 "이 서버의 디스크" 또는 "네트워크 저장소 (NFS)"다.

### 연결이 끊겼을 때

저장소가 보이지 않으면 서버는 **파일 쓰기를 거부한다**(끊긴 저장소 자리의 빈 폴더에 쓰는 사고를 막으려는 것이다). 관리 화면에 "파일 저장소와 연결이 끊겨 파일 쓰기가 멈췄습니다"가 뜨고, 사용자는 파일 탭에서 파일을 열거나 올릴 수 없다. 채팅과 메일 본문은 그대로 동작한다.

- NFS: NAS 가 켜져 있는지, 이 서버와 NAS 사이 네트워크가 살아 있는지 확인한다.
- 이 서버의 디스크: 저장소 디스크가 서버에 붙어 있는지 확인한다.
- 연결되면 자동으로 다시 붙는다. "다시 확인"으로 바로 볼 수 있다.

| 화면의 사유 | 뜻 |
|---|---|
| 저장소 표식이 보이지 않습니다 | 저장소가 붙지 않았거나 다른(빈) 폴더가 붙었다 |
| 다른 설치의 저장소가 붙어 있습니다 | 표식의 설치 id 가 이 서버의 것과 다르다 — 엉뚱한 공유를 연결했다 |
| 저장소가 응답하지 않습니다 | NFS 서버가 응답하지 않는다 |

알려진 한계: 쓰기를 막는 것은 파일 탭과 문서 편집의 저장이다. 채팅 첨부처럼 다른 길로 저장소에 쓰는 기능은 아직 막지 않는다. NFS 가 끊긴 동안 저장소를 읽는 요청은 NFS 가 돌아올 때까지 기다린다([installer.md](installer.md) 12절).

### 저장 위치 옮기기

이 서버의 디스크와 NFS 사이를 설치 후에 바꾸는 화면은 없다. 전체 백업(파일 포함)을 만들고 "백업에서 복원"으로 새 위치를 정하는 것이 문서화된 길이다.

관리 › 저장소·백업의 "파일 저장소 종류"에는 S3 호환 오브젝트 저장소로 바꾸는 설정도 있다(바꾼 뒤의 새 파일부터 그쪽에 저장된다). 설치 관리자의 저장소 점검·표식·검수는 이 서버의 디스크와 NFS 만 다룬다.

## 5. 인증서

관리 › 보안·SSL 의 **인증서** 카드에 종류, 접속 주소, 만료일, 발급자가 보인다.

| 종류 | 갱신 |
|---|---|
| 자동 발급 (Let's Encrypt) | 자동으로 갱신된다. 접속 주소가 계속 이 서버를 가리키고 80번이 밖에서 닿아야 한다 |
| 올린 인증서 | 만료 전에 새 인증서를 이 카드에서 올린다 |
| 임시 인증서 (자체 서명) | 브라우저가 경고를 보여 준다. 이 카드에서 발급하거나 올린다 |
| 프록시가 처리 | 앞단 프록시에서 발급하고 갱신한다. 여기서는 바꾸지 않는다 |

**다시 발급 / 바꾸기.** 카드에서 자동 발급을 다시 요청하거나, 가지고 있는 인증서와 개인 키를 올린다. 바꿀 수 있는 방향은 임시 → 자동 발급·올리기, 자동 발급 → 올리기다. 발급이 실패하면 쓰던 인증서를 그대로 둔다. 성공하면 웹 서버와 회의 서버가 새 인증서를 읽고, 보류돼 있던 구역 연결(코드 저장소의 로그인 연동)을 다시 건다.

- **사설 CA 가 내준 인증서**를 올릴 때는 인증서 파일에 **발급 CA(체인)를 함께** 넣는다(서버 인증서 뒤에 중간·루트 인증서를 이어 붙인 PEM). 함께 온 CA 는 코드 저장소 컨테이너가 믿도록 넣어 주므로 코드 저장소의 로그인 연동이 이어진다. 서버 인증서 한 장만 올리면 코드 저장소는 그 인증서를 믿지 못해 연결이 보류로 남는다. 사용자의 브라우저와 기기가 그 CA 를 믿게 하는 일은 따로 해야 한다.
- 자동 발급에는 인증서에 들어갈 이름(접속 주소, 내장 메일의 `mail.<메일 도메인>`, 회의 중계의 `turn.<접속 주소>`, 격리 브라우저의 `rbi.<접속 주소>`)이 모두 DNS 에 있어야 한다.
- 프록시 뒤 구성에서는 프록시를 거치지 않는 이름(메일·회의)에 자체 서명 인증서가 쓰인다. 메일 앱에서 인증서 경고가 뜰 수 있다.
- 실제 Let's Encrypt 발급과 갱신은 아직 실서버에서 확인하지 못했다([installer.md](installer.md) 13절).

## 6. 메일 DNS 레코드

내장 메일 서버로 메일을 제대로 주고받으려면 메일 도메인에 레코드 다섯 개가 필요하다. 관리 › 구역에서 메일의 "설정"을 열면 **등록할 값과 지금 상태**(확인됨 · 아직 없음 · 값이 다름 · 확인 불가)를 보여 주고, 값을 복사할 수 있다.

| 종류 | 이름 | 쓰임 |
|---|---|---|
| MX | 메일 도메인 | 이 도메인의 메일을 받을 서버 |
| A | `mail.<메일 도메인>` | 메일 서버의 주소 |
| TXT (SPF) | 메일 도메인 | 이 도메인으로 보낼 수 있는 서버 |
| TXT (DKIM) | 화면에 나온 이름 | 보낸 메일의 서명을 확인할 공개 키(설치 때 만든 키) |
| TXT (DMARC) | `_dmarc.<메일 도메인>` | 위 둘이 맞지 않을 때의 처리 |

- 레코드가 빠지면 보낸 메일이 스팸으로 분류될 수 있다.
- 밖에서 이 서버의 25번 포트로 들어올 수 있어야 메일을 받는다. 통신사가 25번을 막는 회선이면 외부 발신 서버로 바꾼다.
- 받는 쪽 서버가 보낸 서버의 역방향 이름(PTR)을 확인하는 경우가 많다. PTR 은 서버를 빌려준 곳(클라우드·통신사)에서 설정한다.
- 서버를 옮겨도 DKIM 키는 백업과 함께 따라온다 — 등록해 둔 레코드를 그대로 쓴다.

## 7. 로그

컨테이너 이름은 `ws-` 로 시작한다. 설치 관리자는 `jw-installer`.

```bash
docker ps --format '{{.Names}}\t{{.Status}}'      # 무엇이 떠 있나
docker logs --tail 200 ws-backend                 # 서버(API)
docker logs --tail 200 ws-nginx                   # 웹 진입점
docker logs -f ws-mailserver                      # 메일 서버(따라 보기)
docker logs jw-installer                          # 설치 관리자
```

| 컨테이너 | 무엇 |
|---|---|
| `ws-nginx` · `ws-frontend-react` · `ws-backend` | 웹 진입점 · 화면 · 서버(API) |
| `ws-postgres` · `ws-redis` | 데이터베이스 · 캐시 |
| `ws-certbot` | 인증서 자동 발급·갱신 |
| `ws-mailserver` | 메일 구역(내장 메일 서버) |
| `ws-onlyoffice` | 문서 편집 구역 |
| `ws-livekit` · `ws-egress` · `ws-audiorelay` | 회의 구역(회의 서버 · 녹화 · 무손실 오디오) |
| `ws-gitea` | 코드 저장소 구역 |
| `ws-searxng` · `ws-docconv` · `ws-sandbox` | AI 도우미 구역(웹 검색 · 문서 변환 · 코드 실행) |
| `ws-sso` · `ws-ldap` | SSO·LDAP 제공 애드온 |
| `ws-rbi-netfilter` | 격리 브라우저 애드온 |

- **로그 로테이션**: 컨테이너 로그는 서비스마다 10 MB 파일 5개까지만 둔다(compose 에 정해져 있다). 오래된 것은 밀려난다.
- **설치·구역·업데이트의 기록**: 설치 단계는 `<설치 폴더>/state/logs/<단계>.log`, 구역 작업은 관리 › 구역의 "기록 보기", 업데이트는 관리 › 업데이트 › 기록(내려받을 수 있다).
- **요청 번호**: 사용자의 오류 화면에 "요청 번호"가 나오면 그 값으로 서버 로그를 찾는다 — `docker logs ws-backend 2>&1 | grep <요청 번호>`.
- **접근 로그·감사**: 관리 › 접근 로그.
- **서비스 상태**: 관리 › 서비스 상태.

버그를 신고할 때는 관련 컨테이너의 로그 끝부분을 붙인다. 로그에 주소·계정 이름 같은 것이 섞여 있을 수 있으니 올리기 전에 확인한다.

## 8. 디스크

```bash
df -h                       # 디스크
docker system df -v         # 이미지·볼륨이 쓰는 공간
```

| 볼륨 | 내용 |
|---|---|
| `ws-storage-data` | 파일 저장소(이 서버의 디스크를 골랐을 때) |
| `ws-postgres-data` | 데이터베이스 |
| `ws-mail-data` · `ws-mail-state` · `ws-mail-logs` | 메일함 · 메일 상태 · 메일 로그 |
| `ws-gitea-data` | 코드 저장소 |
| `ws-backups` | 관리 화면의 백업과 업데이트 직전 백업 |
| `ws-egress-out` | 회의 녹화의 임시 출력 |
| `ws-certbot-data` | 인증서 |
| `ws-plugins-data` | 올려서 설치한 플러그인 |

- **백업이 가장 빨리 찬다.** 예약 백업의 보존 일수를 정하고, 받아서 다른 곳에 옮긴 것은 목록에서 지운다.
- **사용자별 할당과 휴지통 보관 기간**은 관리 › 저장소·백업에서 정한다.
- **`docker image prune -a` 를 조심한다.** 복원 지점으로 돌아가려면 그 버전의 이미지가 서버에 남아 있어야 한다. 업데이트가 성공하면 쓰이지 않게 된 옛 이미지는 설치 관리자가 스스로 치운다.
- 볼륨은 지우지 않는다(`docker volume rm`, `docker compose down -v`, `docker system prune --volumes`). 데이터가 사라진다.

## 9. 흔한 문제

| 증상 | 볼 곳 |
|---|---|
| 관리 › 구역·업데이트에 "설치 관리자에 연결하지 못했습니다" | `docker ps` 에 `jw-installer` 가 있는지 본다. 멈춰 있으면 `docker start jw-installer` |
| 파일을 올리거나 열 수 없다 | [4절](#4-파일-저장소) — 저장소 연결 |
| 점검 화면이 풀리지 않는다 | 관리 › 업데이트. 관리자의 선택을 기다리는 중이거나 되돌림이 멈춘 상태다([2절](#2-업데이트)) |
| 브라우저가 인증서 경고를 보여 준다 | [5절](#5-인증서) — 임시 인증서이거나 만료됐다 |
| 보낸 메일이 스팸으로 간다 / 메일이 들어오지 않는다 | [6절](#6-메일-dns-레코드) — 레코드와 25번 포트 |
| 초대·비밀번호 재설정 메일이 가지 않는다 | 메일 구역이 꺼져 있으면 시스템 메일을 보내지 못한다. 메일 구역을 켜거나 외부 발신 서버를 설정한다 |
| 밖에서 회의에 들어오지 못한다 | 회의 포트(UDP 7882-7892, UDP 3478, TCP 7881)가 밖에서 닿는지, 관리 › 구역의 회의 설정에서 공인 주소가 맞는지 |
| 코드 저장소에 "연결 보류" | [1절](#1-구역-켜고-끄기) — 신뢰되는 인증서로 바꾼 뒤 "다시 연결" |
| 관리자 비밀번호를 잊었다 | `docker exec jw-installer jw reset-admin <아이디>`([install.md](install.md#관리자-비밀번호를-잊었을-때)) |
| 접속하면 "관리자 계정을 준비하는 중입니다" 가 나온다 | 관리자 계정이 하나도 없다. 설치가 아직 진행 중이면 설치 관리자 화면(`https://<서버 주소>:8443`)에서 끝나기를 기다린다. 설치가 끝난 서버라면(관리자를 모두 지운 경우 등) 서버 터미널에서 만든다: `docker exec -it -u appuser ws-backend python -m app.cli seed-admin --username <아이디>`. 설치 관리자로 설치한 서버는 웹에서 첫 관리자를 만들 수 없다 |
| 최초 설정 화면이 "설정 토큰"을 묻는다 | 직접 띄운 서버다. `docker compose logs backend \| grep "setup token"` 의 가장 최근 값을 넣는다. 다시 발급: `docker compose exec backend python -m app.cli setup-token`([deployment.md](deployment.md#첫-관리자-만들기)) |
| 서버(backend)가 뜨지 않고 로그에 비밀값 이름이 나온다 | 약한·기본 비밀값으로는 뜨지 않는다. 직접 띄운 설치에서 생긴다 — [CONFIG.md](CONFIG.md)의 "비밀값" |
| 서버가 뜨지 않고 "DB 스키마 버전이 … 높습니다" | DB 가 코드보다 새것이다(이미지만 이전 버전으로 되돌린 경우). [data-safety.md](data-safety.md) 5절 |
| 공유기 뒤 서버에서 안에서는 되는데 밖에서 안 된다 | 공유기의 포트 넘김. 필요한 포트는 [install.md](install.md#포트) |
