# 업데이트

본 문서는 업데이트의 처리 내용과 실패 시 동작을 기술한다. 관리 화면의 조작 순서는 [operate.md](operate.md#2-업데이트)를 참조한다.

## 업데이트 경로

| 설치 방식 | 업데이트 방법 |
|---|---|
| 설치 관리자(마법사·응답 파일) | 관리 › 업데이트 화면 — 설치 관리자가 릴리스 단위로 수행한다(아래) |
| 설치 관리자 없이 수동 구성([deployment.md](deployment.md)) | `scripts/update.sh`(본 문서 말미의 "수동 설치") |

## 설치 관리자로 설치한 서버

### 처리 절차

1. **확인.** 설치 관리자가 6시간 주기(소폭의 지연 편차 적용)로 채널 파일을 수신하여 서명·만료·순번을 검증한다. 수신만 수행하며, 서버의 식별자·버전·통계는 전송하지 않는다. 신규 버전이 존재하면 관리 › 업데이트에 변경 내용과 함께 표시된다.
2. **시작.** 관리자가 "업데이트"를 선택하면 5분간의 사전 공지가 전체 사용자 화면에 표시된다("지금 바로 시작"·"취소" 가능). 사전 공지가 종료되면 점검 모드로 전환된다 — 일반 사용자의 요청은 차단되고 점검 화면이 표시된다.
3. **적용.** 사전 점검 → 자동 백업(DB·설정) → 이미지 pull → DB 변경 → 구역 교체 → 상태 확인 순으로 진행한다. 구역 교체 단계에서 backend 는 최후에 교체되며, 이후 설치 관리자 자신도 신규 버전으로 교체된다.
4. **종료.** 점검 모드가 해제되고 이력이 기록된다(수행자·일시·이전 버전과 대상 버전·소요 시간·단계별 기록, 1년 보관).

### 실패 시 동작

| 실패 지점 | 동작 |
|---|---|
| DB 변경 **이전**(사전 점검·백업·이미지 pull) | 진행을 중단하고 관리자가 선택한다: "이 단계부터 다시" 또는 "되돌리기". 변경된 사항이 없으므로 "되돌리기"는 점검 모드만 해제한다 |
| DB 변경 이후 | 확인 절차 없이 롤백한다 — 이전 이미지·이전 설정으로 교체하고 DB 를 직전 백업으로 복원한다 |
| 자동 업데이트 | 단계와 무관하게 롤백하고 자동 업데이트를 중지한다. 관리자가 "다시 활성화"를 선택하여야 다음 적용 시간대부터 재시도한다 |
| 롤백 실패 | 워크스페이스는 중지된 상태로 유지되며, 화면에 중단된 단계와 백업의 위치가 표시된다. "다시 시도"가 가능하며, 수동 복구 절차는 [data-safety.md](data-safety.md) 4절에 기술한다 |

롤백의 대상은 **DB 와 설정**이다. 파일 저장소는 백업 대상도 롤백 대상도 아니다 — 이에 따라 점검 모드 중에는 쓰기를 차단한다.

### 적용 방식 및 채널

- **수동**(기본): 신규 버전의 존재만 통지한다.
- **자동**: 적용 시간대(기본 03:00~05:00, 서버 시간) 내에서 **공개 후 3일이 경과한 릴리스만** 적용한다. 시작 5분 전에 사전 공지가 표시된다.
- **채널**: Stable(기본) / Beta. Beta 채널은 Stable 릴리스도 수신한다.
- **Stable 채널 복귀**: 채널만 변경하는 경우 Stable 이 현재 버전 이상이 될 때까지 대기한다(하위 버전으로 내려가지 않는다). 대기하지 않으려는 경우 "시험판 이전 상태로 복원"을 사용한다 — Beta 로 최초 전환하기 직전에 별도 보관한 백업으로 복원한다(이후 누적된 DB 변경은 소실된다).
- 단일 단계로 도달할 수 없는 버전은 경유 버전을 순차적으로 설치한다(1회의 확인으로 진행하며, 버전마다 백업을 생성한다).

### 복원 지점

업데이트마다 생성되는 백업이 복원 지점이다. 최근 3개를 보관하며(시험판 이전 백업은 별도 보관), 관리 › 업데이트 › 롤백에서 선택하여 해당 버전·해당 시점의 DB 로 복원할 수 있다. 복원 이후 재차 업데이트할 수 있다.

### 오프라인 환경의 업데이트

1. 인터넷에 연결된 PC 에서 대상 버전의 **오프라인 번들**(`just-workspace-<버전>-offline.tar`)을 내려받는다.
2. 관리 › 업데이트 › 오프라인에서 업로드하거나, 서버로 전송한 후 해당 경로를 입력한다(설치 폴더 하위여야 한다).
3. 서명과 버전의 검증이 완료되면 **추가로 필요한 이미지**(데이터베이스·웹 서버 등 외부 이미지)의 목록과, 이를 PC 에서 파일로 저장하는 명령이 표시된다. 서버에 이미 존재하는 이미지는 "있음"으로 표시된다.
4. 누락된 이미지 파일을 업로드하면 적용이 가능하다. 이후 절차는 온라인 업데이트와 동일하다.

### 사전 준비 사항

- **공개 키.** 채널의 서명을 검증하는 키다. 설치 관리자 이미지에 포함되어 있다(리포의 `installer/keys/`). 다른 채널을 사용하는 경우 `<설치 폴더>/state/update/keys/` 에 해당 채널의 `*.pub` 파일을 배치한다(최대 2개) — 해당 위치에 키가 존재하면 이미지에 포함된 키는 사용하지 않는다. 어느 위치에도 키가 없으면 화면에 "구성되지 않음"으로 표시되며 확인·적용을 수행하지 않는다.
- **채널 주소.** 기본값은 공식 채널이다. 사내 미러를 사용하는 경우 설치 관리자의 `JW_UPDATE_CHANNEL_URL` 로 변경한다.

상세 구조(자기 교체, 번들, 보관 규칙)는 [installer.md](installer.md) 16절, 화면이 호출하는 API 는 [update-api.md](update-api.md), 채널·릴리스의 형식은 [releases.md](releases.md)에 기술한다.

## DB 마이그레이션

스키마에는 버전이 부여된다(`schema_migrations` 테이블, 코드가 요구하는 버전은 `backend/app/db/schema_version.py`). 상세 사항은 [data-safety.md](data-safety.md) 1절에 기술한다.

- 변경은 번호가 부여된 단계로만 수행한다(`backend/app/db/migrations.py`). 단계 하나가 하나의 트랜잭션이며, 역방향(다운그레이드) 단계는 제공하지 않는다
- 적용: `python -m app.cli migrate`(`--check`, `--status`). 동시에 하나만 실행된다(**PostgreSQL 세션 advisory lock**)
- 컨테이너 기동 시 워커보다 먼저 1회 적용한다. 적용에 실패하였거나 DB 가 코드보다 상위 버전이면 **서버가 기동하지 않는다**. `JW_MIGRATE_ON_START=0` 이면 적용하지 않고 버전만 확인한다
- 외부 구성 요소(PostgreSQL, Redis, Gitea 등)의 버전을 상향하면 데이터 형식이 함께 상향되어 이전 버전으로 복귀할 수 없는 경우가 있다. 조건은 `docker-compose.yml` 의 해당 이미지 주석에 명시되어 있다 — 모든 경우에 **백업을 선행**한다

## 버전 관리

- 제품 버전의 단일 출처는 리포 루트의 `VERSION` 파일이다. backend 는 환경변수 `JW_APP_VERSION` → 이미지에 내장된 값 → `VERSION` 순으로 조회하며(`backend/app/version.py`), `/api/health` 가 이를 반환한다.
- 컨테이너 이미지 버전: `docker-compose.yml`(다이제스트 고정 + 버전 주석)
- 의존성: `backend/requirements.txt`(전부 `==` 고정), `frontend-react/package.json`

## 수동 설치(소스 빌드)

```bash
bash scripts/update.sh              # git pull --ff-only → 빌드 → 다시 띄우기 → 확인
bash scripts/update.sh --no-pull    # git pull 생략(지금 폴더의 소스로)
bash scripts/update.sh --rollback   # 직전 업데이트 때 적어 둔 이미지로 되돌린다
```

현재 실행 중인 자체 빌드 이미지에 롤백용 태그(`<이름>-rollback`)를 부여하여 `.update-rollback` 에 기록하고, 활성화된 프로파일의 자체 빌드 이미지를 재빌드하여 `docker compose up -d` 를 실행한 후 backend 의 상태(`/api/health`)를 확인한다. 재기동 중에는 접속이 일시 중단된다. **자동 롤백은 수행하지 않는다** — 실패 시 `--rollback` 을 안내할 뿐이다. 본 스크립트는 DB 를 백업하지 않으므로 사전에 `scripts/backup.sh --kind pre-update` 를 실행하여야 한다. `scripts/health.sh` 는 Docker·컨테이너·DB·Redis·API·디스크·NFS·SSL 만료를 점검한다(`--json`).
관리 › 업데이트 화면은 본 구성에서 "여기서 업데이트할 수 없습니다"로 표시된다(설치 관리자가 존재하지 않는다).

## 롤백(수동 설치)

```bash
bash scripts/update.sh --rollback          # 붙여 둔 -rollback 태그의 이미지를 원래 이름에 다시 붙이고 컨테이너를 다시 만든다
# 또는 특정 커밋
git log --oneline -10 && git checkout <해시> && docker compose build && docker compose up -d
```

주의: 이미지의 롤백만으로는 복구되지 않는 경우가 있다. 업데이트가 스키마 버전을 상향한 경우 이전 이미지의 backend 는 **기동하지 않는다**(DB 가 코드보다 상위 버전) — 업데이트 직전 백업으로 DB 도 복원하여야 한다(`scripts/restore.sh`, [data-safety.md](data-safety.md) 4·5절). 데이터 버전을 상향한 컨테이너(Redis 8 RDB, Gitea 28 DB)도 백업 복원이 유일한 롤백 수단이다.

## 백업

```bash
sudo bash scripts/backup.sh [받을-폴더]              # 전체 백업을 .jwbak 한 개로(30일 보존)
sudo bash scripts/backup.sh --kind pre-update        # DB 와 설정만(업데이트 직전)
sudo bash scripts/restore.sh <백업 파일>             # 검증 → 정지 → DB → 스키마 → 나머지 → 시작 → 확인
```

위 스크립트는 수동 구성 서버용이다. 백업 형식은 단일하며(관리 화면·스크립트·CLI·설치 관리자 공통), 포함·제외 항목(Redis, NFS 의 파일), 암호화 키, 복원의 단계와 실패 시 동작은 [data-safety.md](data-safety.md)에 기술한다. 관리 › 저장소·백업 화면의 백업은 백업 볼륨(`BACKUP_VOLUME`, 기본 `ws-backups`)에 저장된다. 복원은 앱 내에서 수행하지 않는다 — 설치 관리자로 설치한 서버의 절차는 [operate.md](operate.md#3-백업-복원-및-서버-이전)를 참조한다.
