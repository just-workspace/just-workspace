# 업데이트

업데이트가 무엇을 하고, 실패하면 어떻게 되는지를 적는다. 관리 화면에서 누르는 순서는 [operate.md](operate.md#2-업데이트).

## 두 가지 길

| 설치한 방법 | 업데이트하는 방법 |
|---|---|
| 설치 관리자(마법사·답변 파일) | 관리 › 업데이트 화면 — 설치 관리자가 릴리스 단위로 한다(아래) |
| 설치 관리자 없이 직접([deployment.md](deployment.md)) | `scripts/update.sh`(맨 아래 "수동 설치") |

## 설치 관리자로 설치한 서버

### 무엇이 일어나는가

1. **확인.** 설치 관리자가 여섯 시간마다(조금씩 어긋나게) 채널 파일을 받아 서명·만료·순번을 확인한다. 받기만 한다 — 서버의 식별자·버전·통계를 보내지 않는다. 새 버전이 있으면 관리 › 업데이트에 변경 내용과 함께 보인다.
2. **시작.** 관리자가 "업데이트"를 누르면 5분 예고가 전 사용자의 화면에 뜬다("지금 바로 시작"·"취소" 가능). 예고가 끝나면 점검 상태다 — 일반 사용자의 요청은 막히고 점검 화면이 보인다.
3. **적용.** 사전 점검 → 자동 백업(DB·설정) → 이미지 받기 → DB 변경 → 구역 교체 → 상태 확인. 구역을 바꾸는 동안 backend 는 맨 마지막에 바뀌고, 그 뒤 설치 관리자 자신도 새 버전으로 바뀐다.
4. **끝.** 점검이 풀리고 기록에 남는다(누가·언제·어느 버전에서 어느 버전으로·걸린 시간·단계별 기록, 1년 보관).

### 실패하면

| 어디서 | 어떻게 되나 |
|---|---|
| DB 변경 **전**(사전 점검·백업·이미지 받기) | 멈추고 관리자가 고른다: "이 단계부터 다시" 또는 "되돌리기". 아직 바뀐 것이 없으므로 되돌리기는 점검만 푼다 |
| DB 변경부터 | 묻지 않고 되돌린다 — 이전 이미지·이전 설정으로 바꾸고 DB 를 직전 백업으로 복원한다 |
| 자동 업데이트 | 어느 단계든 되돌리고, 자동 업데이트를 멈춘다. 관리자가 "다시 켜기"를 눌러야 다음 시간대부터 다시 시도한다 |
| 되돌림도 실패 | 워크스페이스는 멈춘 채로 남고, 화면에 어느 단계에서 멈췄는지와 백업의 위치가 나온다. "다시 시도"가 되고, 손으로 하는 절차는 [data-safety.md](data-safety.md) 4절 |

되돌림은 **DB 와 설정**을 되돌린다. 파일 저장소는 백업하지도 되돌리지도 않는다 — 그래서 점검 동안 쓰기를 막는다.

### 방식과 채널

- **수동**(기본): 새 버전을 알리기만 한다.
- **자동**: 적용 시간대(기본 03:00~05:00, 서버 시간) 안에서, **나온 지 3일 지난 릴리스만** 적용한다. 시작 5분 전에 예고가 뜬다.
- **채널**: Stable(기본) / Beta. Beta 채널은 Stable 릴리스도 받는다.
- **Stable 로 돌아오기**: 채널만 바꾸면 Stable 이 지금 버전 이상이 될 때까지 기다린다(내려가지 않는다). 기다리기 싫으면 "시험판 이전 상태로 복원" — Beta 로 처음 올리기 직전에 따로 보관해 둔 백업으로 돌아간다(그 뒤에 쌓인 DB 변경은 사라진다).
- 한 번에 갈 수 없는 버전이면 거쳐야 하는 버전을 차례로 설치한다(한 번의 확인으로, 버전마다 백업).

### 복원 지점

업데이트할 때마다 뜬 백업이 복원 지점이다. 최근 3개를 두고(시험판 이전 백업은 따로), 관리 › 업데이트 › 되돌림에서 골라 그 버전·그 시점의 DB 로 돌아갈 수 있다. 돌아간 뒤에는 다시 올릴 수 있다.

### 인터넷이 없는 서버

1. 인터넷이 되는 PC 에서 그 버전의 **묶음 파일**(`just-workspace-<버전>-offline.tar`)을 받는다.
2. 관리 › 업데이트 › 오프라인에서 올리거나, 서버로 옮긴 뒤 그 경로를 적는다(설치 폴더 아래여야 한다).
3. 서명과 버전을 확인하고 나면 **추가로 필요한 이미지**(데이터베이스·웹 서버처럼 남이 만든 구성 요소)의 목록과, 그것을 PC 에서 파일로 받는 명령이 나온다. 서버에 이미 있는 것은 "있음"으로 나온다.
4. 빠진 이미지 파일을 올리면 적용할 수 있다. 이후는 온라인과 같다.

### 준비해야 하는 것

- **공개 키.** 채널의 서명을 확인하는 키다. 설치 관리자 이미지에 들어 있다(리포의 `installer/keys/`). 다른 채널을 쓰려면 `<설치 폴더>/state/update/keys/` 에 그 채널의 `*.pub` 파일을 넣는다(둘까지) — 거기에 키가 있으면 이미지의 키는 쓰지 않는다. 어디에도 키가 없으면 화면에 "구성되지 않음"으로 나오고 확인·적용을 하지 않는다.
- **채널 주소.** 기본은 공식 채널이다. 사내 미러를 쓰면 설치 관리자의 `JW_UPDATE_CHANNEL_URL` 로 바꾼다.

자세한 구조(자기 교체, 번들, 보관 규칙)는 [installer.md](installer.md) 16절, 화면이 부르는 API 는 [update-api.md](update-api.md), 채널·릴리스의 형식은 [releases.md](releases.md).

## DB 마이그레이션

스키마에는 버전이 있다(`schema_migrations` 표, 코드가 요구하는 버전은 `backend/app/db/schema_version.py`). 자세한 것은 [data-safety.md](data-safety.md) 1절.

- 변경은 번호 붙은 단계로만 한다(`backend/app/db/migrations.py`). 단계 하나가 한 트랜잭션이고 되돌리는 단계는 없다
- 적용: `python -m app.cli migrate`(`--check`, `--status`). 한 번에 하나만 돈다(**PostgreSQL 세션 advisory lock**)
- 컨테이너가 뜰 때 워커보다 먼저 한 번 적용한다. 적용에 실패했거나 DB 가 코드보다 새것이면 **서버가 뜨지 않는다**. `JW_MIGRATE_ON_START=0` 이면 적용하지 않고 버전만 확인한다
- 다른 곳에서 만든 구성 요소(PostgreSQL, Redis, Gitea 등)의 버전을 올리면 데이터 형식이 함께 올라가 이전 버전으로 돌아갈 수 없는 경우가 있다. 조건은 `docker-compose.yml` 의 그 이미지 옆 주석에 있다 — 전부 **백업 먼저**

## 버전

- 제품 버전의 단일 출처는 리포 루트의 `VERSION` 파일이다. backend 는 환경변수 `JW_APP_VERSION` → 이미지에 구운 값 → `VERSION` 순으로 읽고(`backend/app/version.py`), `/api/health` 가 돌려준다.
- 컨테이너 이미지 버전: `docker-compose.yml`(다이제스트 고정 + 버전 주석)
- 의존성: `backend/requirements.txt`(전부 `==` 고정), `frontend-react/package.json`

## 수동 설치(소스 빌드)

```bash
bash scripts/update.sh              # git pull --ff-only → 빌드 → 다시 띄우기 → 확인
bash scripts/update.sh --no-pull    # git pull 생략(지금 폴더의 소스로)
bash scripts/update.sh --rollback   # 직전 업데이트 때 적어 둔 이미지로 되돌린다
```

지금 돌고 있는 우리 이미지에 되돌릴 때 쓸 태그(`<이름>-rollback`)를 붙여 `.update-rollback` 에 적어 두고, 켜진 프로파일의 우리 이미지를 다시 빌드해 `docker compose up -d` 한 뒤 backend 의 상태(`/api/health`)를 본다. 다시 뜨는 동안 접속이 잠깐 끊긴다. **자동으로 되돌리지는 않는다** — 실패하면 `--rollback` 을 안내할 뿐이다. 이 스크립트는 DB 를 백업하지 않으므로 먼저 `scripts/backup.sh --kind pre-update` 를 돌린다. `scripts/health.sh` 는 Docker·컨테이너·DB·Redis·API·디스크·NFS·SSL 만료를 점검한다(`--json`).
관리 › 업데이트 화면은 이 구성에서 "여기서 업데이트할 수 없습니다"로 나온다(설치 관리자가 없다).

## 롤백(수동 설치)

```bash
bash scripts/update.sh --rollback          # 붙여 둔 -rollback 태그의 이미지를 원래 이름에 다시 붙이고 컨테이너를 다시 만든다
# 또는 특정 커밋
git log --oneline -10 && git checkout <해시> && docker compose build && docker compose up -d
```

주의: 이미지만 되돌리면 안 되는 경우가 있다. 업데이트가 스키마 버전을 올렸으면 이전 이미지의 backend 는 **뜨지 않는다**(DB 가 코드보다 새것) — 업데이트 직전 백업으로 DB 도 복원해야 한다(`scripts/restore.sh`, [data-safety.md](data-safety.md) 4·5절). 데이터 버전을 올린 컨테이너(Redis 8 RDB, Gitea 28 DB)도 백업 복원이 유일한 롤백이다.

미리 빌드한 이미지를 만들고 채널에 올리는 절차는 [releases.md](releases.md)(빌드 워크플로 `.github/workflows/build-images.yml`, 서명, 승격).

## 백업

```bash
sudo bash scripts/backup.sh [받을-폴더]              # 전체 백업을 .jwbak 한 개로(30일 보존)
sudo bash scripts/backup.sh --kind pre-update        # DB 와 설정만(업데이트 직전)
sudo bash scripts/restore.sh <백업 파일>             # 검증 → 정지 → DB → 스키마 → 나머지 → 시작 → 확인
```

위 스크립트는 직접 띄운 서버용이다. 형식은 하나이고(관리 화면·스크립트·CLI·설치 관리자 공통), 무엇이 들어가고 빠지는지(Redis, NFS 의 파일), 암호화 키, 복원의 단계와 실패 시 동작은 [data-safety.md](data-safety.md). 관리 › 저장소·백업 화면의 백업은 백업 볼륨(`BACKUP_VOLUME`, 기본 `ws-backups`)에 쌓인다. 복원은 앱 안에서 하지 않는다 — 설치 관리자로 설치한 서버의 절차는 [operate.md](operate.md#3-백업과-복원-서버-이전).
